竞争格局与产品定位

微信生态内已有多款"消息 → 提醒"类工具。这一节对比它们与 WeSchedule 的差异，说明这个项目选择做冲突检测与日程治理而非单纯解析的原因，以及如果平台原生能力下场，项目的应对思路。

竞品信息核实于 2026 年 9 月（功能以各产品当前版本为准）。

Landscape · 竞品全景

微信生态内的同类工具

生态内与"消息转日程"直接相关的有四类：微信官方 AI 助手、腾讯元宝、滴答清单的微信入口、工作 IM 的原生日程。

产品创建方式提醒通道冲突检测主要局限
WeSchedule（本项目） 复制群消息 → 小程序读剪贴板 → DeepSeek 结构化解析（10 字段 + 置信度）→ 确认后保存 微信订阅消息（一次授权一次推送） 有：软/硬分级 + 备选时段 入口需"复制 → 打开"两步；日程库从零积累
腾讯元宝 微信好友聊天，一句话设提醒（2025.12 上线，支持语音与模糊时间） 微信服务通知（不受订阅授权次数限制） 无 单次提醒即终点；微信内暂不支持周期提醒；无日程库与视图管理
微信「小微」 微信原生 AI 助手（2026.6 起灰度内测）：聊天框内"问小微"可总结当前对话、设系统级提醒 系统级待办 / 微信弹窗 未见 仍处内测，2026 年内计划扩大开放；功能边界在持续变化
滴答清单 服务号发消息建任务（自动识别时间）；或把聊天记录转发给"滴答小助手"采集保存 App 推送 + 微信提醒 无（有日历视图，无冲突概念） 转发仅"采集存原文"，不解析时间；无确认编辑环节
企业微信 / 钉钉 / 飞书 工作 IM 原生日程、群消息转日程 系统推送 部分有闲忙 限工作场景与组织内，不覆盖个人微信群

两点值得注意：① 元宝的提醒走微信服务通知，不受小程序"一次授权一次推送"的预算约束，这是平台身份带来的差异；② 「小微」是微信官方能力，入口距离最短，若其覆盖"消息转日程"，入口层的价值会被稀释——这是本项目需要正视的变量。

Position · 差异化定位

不做"提醒生成"，做"日程治理"

把上面的产品放进两个维度里看：横轴是有没有日程库（能否积累并管理），纵轴是处理时刻问题（这件事几点发生、撞没撞）还是容量问题（这一周还排不排得下）。

提醒生成（单次、无积累） 任务清单（有库、无治理） 日程治理（本项目方向）

观察：提醒类工具解决"别忘事"，但都不维护一份可管理的日程库，也不回答"日程之间是否冲突、DDL 的缓冲是否被透支"。这正好对应调研中的第一需求：冲突检测（70.1%）。

Framework · 问题框架

"别撞车" 与 "别过载" 是两件事

撞车：时刻维度的冲突

  • 硬冲突：两个定点事项时间重叠（会议撞会议）——多数日历能做基础检测
  • 软冲突：定点事项落在 DDL 的缓冲区间内——DDL 不是"那一天"，而是"截止前的那段可支配时间"。周四答应聚餐，表面不撞车，实际透支了周日 DDL 的缓冲

WeSchedule 用 is_deadline 这一个可靠字段区分两者，刻意不引入新的 AI 类型判断，避免"类型判错 → 冲突等级被放大"。

过载：容量维度的冲突

  • DDL 堆积：三个作业同周末截止，每个录入时都"不冲突"，到期才发现排不开
  • 会议沼泽：日程表不重叠，但一整天没有整块可支配时间

现有工具问的是"这个时间空不空"，少有人问"这周还剩多少可支配时间"。过载是慢性的，发现时往往已晚。这是比撞车更难被现有工具覆盖的问题。

工程上，过载检测不需要 AI：现有数据结构（date / 起止时间 / is_deadline / fuzzy_time）已足够，规则在本地跑即可，几乎不增加后端成本。

Defense · 防御性思考

如果平台原生能力下场，还剩什么

「小微」正在内测，官方 Agent 天然拥有最短的入口和系统级通道。如果"消息转日程"被原生能力覆盖，这个项目的价值还剩什么。这是设计之初就想清楚的问题。

  • 正视变量：入口层（复制 → 解析）确实可能被原生能力替代，所以本项目不把"解析"当作壁垒，只把它当作入口。
  • 价值落在治理层：冲突检测、DDL 区间管理、负载提示依赖一份持续积累的日程库：用得越久，检测越准。提醒类工具是无状态的，用过即走；治理的价值随使用加深。
  • 把平台约束转成设计决策：个人主体小程序无法写系统日历，于是用"小程序内日程 + 订阅消息"；订阅消息"一次授权一次推送"，于是预备提醒复用同一授权改到前一晚；隐私合规要求下，解析日志只存 input_hash 不留原文。这些约束反而定义了产品的形态。
Next · 下一步规划

如果继续做，按这个顺序

  • badcase 一键上报：解析结果页加"识别有误？"上报入口，用真实 badcase 驱动 prompt 迭代（当前 75% 准确率的第一改进杠杆）。
  • 置信度驱动 UI：低置信度字段标黄并要求确认，让"75% 准确率"对用户透明。
  • 确认页前置当日全景：保存前展示当天已有日程，让首次使用者立刻感知冲突检测的价值。
  • 过载层（V1.1）：周负载条 → DDL 堆积预警 → 准备块自动排程，复用现有 is_prep 与冲突引擎。

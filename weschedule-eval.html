Corpus · 评测集

语料是怎么来的

100 条语料按"消息形态"分七类，每类对应解析链路的一种失败模式。相对时间的锚点统一写死为 2026-07-17（周五），保证同一条语料每次跑出同一个标准答案。

类别条数考察什么样例
A 标准25明确的日期 + 钟点（+ 可选地点），基本盘7月24日周五下午3点在主楼A203开班会
B 相对时间20"明天 / 下周三"这类相对表述能否正确换算成绝对日期明天晚上7点老地方打球
C 模糊10只给"傍晚 / 改天"这类时段词，没有确切钟点下周一傍晚咱们宿舍聚餐
D 多日程10一条消息里含两个及以上事件，考验是否漏掉后一个周六上午10点交实验报告，下午4点班级开会
E 无日程15闲聊与疑问句，考验不误报哈哈哈这个表情包绝了，谁做的
F 截止日10DDL 型消息，需要正确打上 is_deadline数据结构第4次作业7月20日晚12点前提交
G 口语碎片10带表情、错字、改写通知的口语表达志愿活动改到下午两点半了哈，集合还是在西门[捂脸]

来源构成：100 条里 93 条是手写构造（按上表七类逐类补齐），7 条来自真实群聊脱敏，原始种子就取自实际群聊，脱敏后保留原样。这一点如实说明：它意味着这套语料能覆盖我预想到的失败模式，但不能代表真实流量的分布。

切分方式：按 seed=20260717 做一次固定随机切分，dev 80 条 / test 20 条，切分结果落盘在 eval/.split.json。同一份切分贯穿全部三个版本，因此版本之间的差值只来自提示词本身。

Metrics · 指标口径

五层指标与达标线

单看一个分数很容易被误导，所以把"解析对不对"拆成五层分别统计。同一层里也会互相拉扯，最终以端到端为准。

层级怎么算达标线
has_schedule 判定这条消息该不该生成日程（P / R / F1）F1 = 100
误报率E 类（无日程）被判成有日程的比例≤ 5%
事件级 P / R抽出来的事件与标注事件逐个配对后的查准 / 查全—
字段准确率在命中事件里，date / time / location 与标准答案完全一致的比例90% / 80% / 70%
端到端完全正确率该条消息所有标注事件都命中、且每条命中的 date / time / location 全对、且没有多报，才算这条通过≥ 75%

关于 75% 这个口径：端到端是"整条消息完全正确"的严格口径，任何一处字段不一致就判该条失败。它不等于"准确率只有四分之三"：同一次运行的字段准确率是 date 100%、time 89.4%、location 100%。

Badcase · 失败面

改完提示词，错的地方换了位置

逐版把 badcase 落盘对比，失败面发生了方向性迁移，数量也在下降。

版本badcase 条数按类别分布（B 相对时间 / C 模糊 / D 多日程）
v1 · dev15B 4 · C 5 · D 6
v1.1 · dev12B 2 · C 4 · D 6
v1.2 · dev8B 2 · C 0 · D 6
v1.2 · test2B 1 · D 1

v1.1 修掉了什么

补上"时段词 → 钟点"的映射表，并规定"下周X"一律按未来向推算。C 类（模糊时间）的 badcase 从 5 条降到 4 条，time 字段准确率从 83.3% 升到 89.4%。

v1.2 修掉了什么

加了"只要表达了未来的行动意图就必须提取"这条规则，把此前被当成闲聊丢掉的"晚上有空的话一起自习吧"这类消息救回来了。这一版把 C 类 badcase 清零，端到端首次到 75%。

剩下的错集中在哪：v1.2 的 8 条 badcase 里 6 条属于 D 类多日程——一条消息里有多个事件时，排在后面的那个容易漏。这类问题靠加规则不容易解决（规则越多，误报风险越大），更合理的路径是把"识别有误"的上报入口做进产品，用真实 badcase 继续喂养评测集。

Limits · 边界

这套评测不能证明什么

边界说明
语料以手写构造为主93 / 100 条是我按失败模式写的，真实群聊脱敏只有 7 条。它能验证"我预想到的问题有没有被修掉"，不能代表真实流量分布。
金标准与达标线都是自定的标注、指标口径、75% 这条线都由我定义，属于确定性回归测试，数字不能与公开 benchmark 类比。
端到端口径极严整条消息全对才算通过。这也是 75% 看起来不高、但字段准确率接近满分的原因。
未做多模型对比只测了线上实际使用的 deepseek-chat（temperature=0，JSON 模式），没有横向对比其他模型。
没有线上真实流量回流评测集是离线固定的，尚未把线上解析日志接进评测闭环；这是下一步的第一优先项。
完成时点这套闭环在 2026-08-21 的一次会话中集中完成，之后随提示词迭代继续复用。

评测集与线上提示词是两份副本：cloudfunctions/parse/index.js 与 eval/run_eval.py 里各存一份提示词，两边保持逐字一致（各 1804 字符）。一旦线上一份被单独改动，评测分数就不再代表线上表现，改提示词时必须同时改两处。

Privacy · 数据与隐私

解析过程留了什么、不留什么

小程序个人主体，类目"工具-效率"。解析日志表的字段是我自己定的，原则是最小化留存。

项目处理方式
用户的原始消息文本不保存。日志里只留长度 input_len 与哈希 input_hash，可用于排查与去重，但不能还原原文。
解析结果 JSON会落库（output_json），用于回查解析质量。其中包含从消息里抽取的标题、时间、地点等字段。
其他日志字段request_id / prompt_version / model / latency_ms / success / error_code / created_at。
模型 API 密钥只存在于本地 .env 与云函数环境变量，不入仓库、不进对话。仓库里只有 .env.example。
剪贴板读取由微信隐私授权控制，用户可拒绝；拒绝时仅该功能不可用，其余功能不受影响。

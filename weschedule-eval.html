Corpus · 评测集

语料是怎么来的

112 条语料按"消息形态"分八类，每类对应解析链路的一种失败模式。相对时间的锚点统一写死为 2026-07-17（周五），保证同一条语料每次跑出同一个标准答案。

类别条数考察什么样例
A 标准25明确的日期 + 钟点（+ 可选地点），基本盘7月24日周五下午3点在主楼A203开班会
B 相对时间20"明天 / 下周三"这类相对表述能否正确换算成绝对日期明天晚上7点老地方打球
C 模糊10只给"傍晚 / 改天"这类时段词，没有确切钟点下周一傍晚咱们宿舍聚餐
D 多日程10一条消息里含两个及以上事件，考验是否漏掉后一个周六上午10点交实验报告，下午4点班级开会

2026-10-21 新增		1255–128 字、2–5 个事件的长群公告，只进 test 集【期末考试安排】…7月20日上午9:00-11:00在教二301考《数据结构》；7月22日周三下午2:30…
合计112dev 80 / test 32；H 类用 split_hint 钉死在 test，不参与随机切分——加语料不会洗牌 dev，历史数字仍可比

来源构成：112 条里 105 条是手写构造（按上表逐类补齐，每类对应一种已观测到的失败模式），7 条取自真实群聊脱敏——它们的作用是"锚点"：证明这些失败模式来自真实聊天，而不是凭空想象。为什么不追求更多真实样本？因为真实群聊无法覆盖"边界情况"，而这类边界（"傍晚"该映射到几点、DDL 该不该猜钟点）恰恰是模型最容易错的地方。语料不追求代表真实流量分布，只追求复现已知失败模式——这一点在下面的边界表里也是这么写的。

切分方式：按 seed=20260717 做一次固定随机切分，dev 80 条 / test 32 条，切分结果落盘在 eval/.split.json。同一份切分贯穿全部三个版本，三版运行又都在同一天完成、模型版本没变，所以版本之间的差值可以归到提示词本身——跨天重跑不保证这一点。2026-10-21 新增的 12 条长消息只进 test（split_hint 钉死），**dev 的 80 条一字未动**，因此 dev 那列仍可与三个月前的 77.9% 直接比。

Metrics · 指标口径

六项指标与口径

指标怎么算目标 / 备注
has_schedule 判定这条消息该不该生成日程（P / R / F1）F1 目标 100；test 仅 20 条，作旁证
误报率15 条无日程样本里，被判成"有日程"的比例≤ 5%
事件级 P / R抽出来的事件与标注事件逐个配对后的查准 / 查全看趋势，不设线
字段准确率在配对上的事件里，time / location 与标注完全一致的比例≥ 80% / ≥ 70%
整条消息全对率该条消息的所有标注事件都配上、time 与 location 全对、且没有多报，才算这条通过。分母只算该有日程的消息，15 条无日程样本不参与直接给分子/分母，不设线
编造率（新增）标注里本该为空、模型却填了值的次数（time / location 分别计）——用来抓"AI 猜时间"这类用户最难发现的错越低越好；统一标注后 dev 0 · test 0

为什么没有"date 准确率"这一行：事件配对的条件本身要求日期相等，配上了再比日期必然成立——那是一个恒等于 100% 的伪指标。日期错的真实代价体现在事件级 P / R 上：日期不对的事件配不上，直接算漏报。date 只作为配对键使用。

关于分母（这一版改过）：整条全对率的分母只算"该有日程"的消息。15 条闲聊样本没有标注事件，判不出"解析对不对"，放进分母等于把它们全部记成失败。旧版把 E 类留在分母、又从分子里跳过，dev 的 60/68 被写成了 60/80（75.0%）；本页按修正后的口径重算，8-21 那次运行是 88.2%。

test 那列 2026-10-21 变过口径，别与旧值直接比：当天往 test 补了 12 条长消息（55–128 字、2–5 个事件），分母从 17 变 29，通过率因此从 94.1% 变成 89.7%——不是模型退步，是题目变难。长消息暴露的是真弱项：事件级查准率从 95.0 掉到 90.8，原因是模型把"周一到周三由大一负责"这类排班说明逐日拆成了 5 个事件（多报）；另外出现 1 处编造时间（"下班前"被填成 18:00，而标注按规则 5 写 23:59）。dev 侧没动，仍是 95.6%。

数字的来源：v1 / v1.1 取自 2026-08-21 那批运行；v1.2 取自 2026-10-21 重跑（同日先统一标注口径），旧日志归档在 eval/reports/archive_20260821/。"整条消息全对率"按本页修正后的分母口径重算——日志当时的打印值用的是旧分母，重算只是把分母换成"该有日程的消息数"。

同一份 prompt 跑了三遍，差 5 条——其中 3 条是我改了标注：v1.2 在 8-21 是 88.2%（60/68），10-20 是 91.2%（62/68），10-21 统一标注口径后是 95.6%（65/68）。前两次差 2 条（B011、D007），是 temperature=0 也不逐字可复现的证据；第三次的 +3 不是模型变好，是尺子被修正——D003 / D005 / D006 原先的金标准给"周二小组答辩""周日春游""后天体检"填了原文没有的钟点（违反 prompt 规则 4），模型没编造反而被判错，把这三处改成空值后它们自动变对。所以这条曲线只能读成"同一版 prompt 的波动区间 + 标注修正"，不能读成"迭代带来的提升"；dev 68 条的分辨率约 ±2 条（±3pp），折算成精度约 ±5pp——它给得出量级，给不出小数点后的精度。

* 一处历史显示 bug（未改动历史日志）：v1 那次运行里 has_schedule F1 打印成了 9924.4，原因是当时脚本在百分比换算上重复乘了一次 100，正确值应为 99.2。后续版本已修正，v1.1 之后的日志数值正常。

还有一种口径：把"换了个说法"算对：配对规则对同义改写很苛刻——标注"聚餐"、模型写"一起吃饭"，日期时间全对也判失败。脚本里加了一层保守同义词表（聚餐/吃饭、上课/第X节课、开会/组会，且"预答辩"与"正式答辩"强制不合并），放宽后 dev 98.5%（67/68）· test 93.1%（27/29）。主指标不用这个数：同义词表是我定的，拿它当成绩不诚实；它的用途是回答"剩下的错到底是什么性质"。

为什么只看整条全对率：v1.1 那一次，has_schedule 判定准确率从 98.8% 掉到 95.0%（同一版 F1 从 99.2 掉到 97.0），而事件级与整条全对率同期在涨。单项指标会互相拉扯，所以判断一次改动的好坏只认这一个终值：六项指标都留着看，只有它参与决策。

v1.1 修掉了什么

补上"时段词 → 钟点"的映射表，并规定"下周X"一律按未来向推算。C 类（模糊时间）的 badcase 从 5 条降到 4 条，time 字段准确率从 83.3% 升到 89.4%。

v1.2 修掉了什么

加了"只要表达了未来的行动意图就必须提取"这条规则，把此前被当成闲聊丢掉的"晚上有空的话一起自习吧"这类消息救回来了。这一版把 C 类 badcase 清零，整条全对率首次过 88%。

剩下的错是什么性质：dev 剩 3 条、test 剩 3 条（test 里 2 条是新加的长消息），没有一条能归到"模型没读懂原文"——分三类：① 措辞差异 3 条（B005"聚餐"对"一起吃饭"、B006"上课"对"第一节课换教室"、D009"上课"对"第二节课改实验室"），日期时间全对；② 口径未定义 2 条（H002 把"周一到周三由大一负责"逐日拆成 5 个值班事件——排班算不算日程还没定规则；H012 把"下班前"理解成 18:00，而标注按规则 5 写 23:59，模型其实更贴近原意）；③ 偶发日期错 1 条（D007"周五"算成当天，但单独复跑 3 次全对，见下）。结论：短消息侧的失分是判罚口径，长消息侧暴露的是"排班类消息怎么处理"这类规则缺口——两者都不是靠加提示词规则能解决的。

为什么给 D007 单独复跑了 3 次：它是这批里唯一看起来像"规则没吃透"的失败（规则 2 要求"周X"取下一个周五）。但同一 prompt 连跑 3 次，三次都正确给出 2026-07-24——说明它是波动不是稳定错误，和"同一 prompt 两次运行差 2 条"是同一现象。所以没有为它改提示词：加 few-shot 例子会影响其余 12 条含"周X"的语料，收益不明确。这条经验值得记：单条 badcase 先跑 3 次看稳定性，成本 3 次调用，能避免一次错误的 prompt 改动。

Limits · 边界

这套评测不能证明什么

边界说明
语料以手写构造为主105 / 112 条是我按失败模式写的，真实群聊脱敏只有 7 条。它的作用不是"代表真实流量分布"，而是"复现已知失败模式"——那 7 条真实样本是锚点，证明这些模式来自真实聊天。能验证的是"我预想到的问题有没有被修掉"，不是"线上会怎么错"。
金标准与指标口径都是自定的标注、指标口径、分母都由我定义，属于回归测试，数字不能与公开 benchmark 类比。
整条全对的判定很硬一条消息里任何一个字段不一致就整条判失败。所以它比"单条事件的字段准确率"低，比"这条消息能不能用"高——两个数不能直接比。
标注本身曾有错（10-21 已统一）扫出 10 处与 prompt 规则不一致的标注并逐个改正：D003 / D005 / D006 / D010 的金标准给原文没有钟点的日程填了 14:00 / 08:00（违反规则 4「不要猜测」）；C001 / C008 的"傍晚"按规则 3 应映射到 17:00 却空着；D008 的"早上 / 下午 / 晚上"没按映射表。统一之后 dev 从 91.2% 变 95.6%——这 4.4 个点不是模型变好，是尺子变准。
time / location 的准确率只算"配对上"的事件100% 的意思是"能配上的事件里时间全对"，不是"所有事件时间全对"——配不上的事件算在事件级召回（dev 94.8%）里，不进 time 的分母。两个指标要一起看，不能只挑 100% 说。
配对规则会惩罚同义改写（已量化）标注"聚餐"、模型写"一起吃饭"判不上；标注"上课"、模型写"第二节课改实验室"判不上。脚本里加了一层保守同义词表，放宽后 dev 98.5% / test 93.1%。这个数只作诊断，不进主指标——同义词表由我定义，哪些改写算同一件事没有客观标准，把它当成绩就是自定规则自己打分。
样本量决定了精度上限按 Wilson 区间（95% 置信度）算：dev 65/68 的区间是 88%–98%（宽 10.7pp），test 26/29 是 74%–96%。所以"95.6%"只能理解成"这次抽样的点估计"，不能理解成"模型准确率是 95.6%"。要在 95% 置信度下做到 ±5pp 需要约 73 条、±3pp 要约 203 条——与其加同类短消息，不如加没覆盖的场景。
排班 / 值班类说明没有口径"周一到周三由大一同学负责"算不算我的日程、要不要逐日拆开，规则里没写。长消息 H002 的失败正落在这：模型拆成 5 条，标注一条都不算，两边都讲得通。这条先记成缺口，等真实使用里看多了再定。
"下班前"这类表述没有口径规则 5 说 DDL 未给时间填 23:59，但"下班前"其实指向 18:00。H012 模型填 18:00、标注写 23:59，模型的理解反而更贴近原意——这条暴露的是规则的边界，不是模型的问题。
模型本身不可控temperature=0 不等于严格可复现，服务端模型版本与路由都可能变；只有同一天内的重跑可以互相比。
未做多模型对比只测了线上实际使用的 deepseek-chat（temperature=0，JSON 模式），没有横向对比其他模型。
没有线上真实流量回流评测集是离线固定的，尚未把线上解析日志接进评测闭环；这是下一步的第一优先项。

评测集与线上提示词是两份副本：cloudfunctions/parse/index.js 与 eval/run_eval.py 里各存一份提示词，两边保持逐字一致（各 1804 字符）。一旦线上一份被单独改动，评测分数就不再代表线上表现，改提示词时必须同时改两处。

Privacy · 数据与隐私

解析过程留了什么、不留什么

小程序个人主体，类目"工具-效率"。解析日志表的字段是我自己定的，原则是最小化留存。

项目处理方式
用户的原始消息文本不保存。日志里只留长度 input_len 与哈希 input_hash，可用于排查与去重，但不能还原原文。
解析结果 JSON会落库（output_json），用于回查解析质量。其中包含从消息里抽取的标题、时间、地点等字段。
其他日志字段request_id / prompt_version / model / latency_ms / success / error_code / created_at。
模型 API 密钥只存在于本地 .env 与云函数环境变量，不入仓库、不进对话。仓库里只有 .env.example。
剪贴板读取由微信隐私授权控制，用户可拒绝；拒绝时仅该功能不可用，其余功能不受影响。

展开提示词全文（v1.2 · 1804 字符）

规则 2 的取舍——「周X」为什么取下一个而不是当天：模型只拿到日期、拿不到消息的发送时刻，所以"周五下午2点"在周五当天被说出来时，它分不清指的是今天还是下周五。产品侧的选择是宁可往后挪一周，不可往前放一天——解析出已经过去的时间，提醒会直接判 MISSED，用户拿到的是一条永远不会响的废日程；往后挪一周，用户在确认页改一次日期就恢复了。两个方向的代价不对称，选可修复的那一侧。代价也如实写在这：周五早上说"周五下午开会"会被推到下周五，要多改一次。

你是一个日程信息解析器。用户会给你一段从微信群聊复制的文本，你要判断其中是否包含未来的日程安排，并提取为结构化 JSON。

今天的日期是 {ref_date}，星期{ref_weekday}。所有相对时间都必须以这个日期为锚点换算成绝对日期。

规则：
1. 输出且只输出 JSON，不要输出任何解释、markdown 标记或代码块符号。
2. 相对时间归一化：明天、后天、下周X、X月X日（未给年份时取最近一次的未来日期）都要换算成 YYYY-MM-DD。周X 解析为严格晚于今天（{ref_date}）的下一个匹配星期几（未来向、不含当天），除非文本明确"今天/今/这周X"才取当天。
3. 时段词与模糊时间的区分：
若文本含可映射为具体钟点的时段词且未给具体钟点，则 start_time 取下方映射值、fuzzy_time 填 null：早上/早晨/早自习/第一节课 → 08:00；上午 → 10:00；中午/午间 → 12:00；下午 → 14:00；傍晚 → 17:00；晚上/夜里 → 18:00；第二节课 → 10:00；第三节课 → 14:00。
真正模糊、无法确定钟点的情况（如"有空/大概/左右/最近/哪天都行/找时间/碰一下/再说"等），start_time 填 null，fuzzy_time 填原文表述，confidence 不超过 0.6。
日期填充约束：当消息未指向任何具体某一天（仅模糊时段，或"有空/最近/哪天都行/这周末/下午有会"等），date 必须填 null，禁止填 {ref_date} 或推算日；只有能锚定具体某天（明天/后天/周X/日期/下周X）才填 date。
4. 未明确的时间不要猜测编造。只有原文出现或能直接换算的信息才允许填，否则填 null。
5. 截止日（如"23号前交作业""DDL"）：is_deadline 填 true，未给具体时间时 start_time 填 23:59，reminder_minutes 填 1440。
6. 一条文本含多个独立日程时，拆成多个 event。
7. 以下情况 has_schedule 填 false，events 填空数组：纯闲聊寒暄、表情、询问过去的事、广告。注意：只要文本表达了未来的具体行动意图（如自习、开会、办签证、碰毕业论文、约球、聚餐、面试、体检、还书等），即使只有模糊时段（晚上/下午/最近/有空/哪天都行）或未给具体日期，也必须 has_schedule=true 并提取为事件（date 可填 null，fuzzy_time 填原文时段，start_time 填 null）；仅当完全无行动意图才判 false。
8. title 不超过 12 个字，概括事项本身，不要带"请""记得"等语气词。
9. people 只填原文明确出现的参与人，保留原文称呼。
10. location 保留原文最具体的表述，不要补全或推测。
11. confidence 取值 0 到 1，反映你对这条解析整体的把握。字段缺失越多分值越低。
12. 默认提醒：会议和活动 reminder_minutes 填 30，截止日填 1440。

WeSchedule

How · 方案架构

一条自动化的解析链路

微信不支持把消息直接转发进小程序，入口只能是"复制 → 打开小程序 → 读取剪贴板"；云函数调用 DeepSeek 完成结构化解析，落库后通过微信订阅消息实现到点提醒。

技术栈：微信小程序（WXML/WXSS/JS）· 微信云开发（云函数 + 云数据库）· DeepSeek deepseek-chat（temperature=0，JSON 模式）· 微信订阅消息。

Smart · 冲突检测与提醒策略

把调研数据翻译成设计决策

01

保存前检测冲突，并区分"占用时段"和"只有截止时间"

调研依据 · 冲突检测以 70.1% 排在智能功能偏好第一

保存前自动检测时间重叠，在保存页标出，列表页同步给 ⚠ 角标。

怎么分级
  • 硬冲突 两个定点事项重叠（会议撞会议）→ 强提示，并给出备选时段
  • 软冲突 定点事项撞 DDL → 只弱提示，不给改期建议。作业截止本身不占时段，要回答的是"截止前你有没有空干活"

分级只看 is_deadline 这一个已经稳定的字段，不新增 AI 判断，避免"类型判错 → 冲突等级被放大"。

验收口径

分级走规则实现，准确率接近 100%（已知边界：语义级冲突如"午饭撞午饭"不识别）。

02

只给建议，不替用户改日程

调研依据 · "识别不准"顾虑均值 4.08 排第一 → 该由人拍板的事不交给模型

硬冲突给 1–2 个可一键采纳的备选时段（"改为周三 16:00？"点一下即改），默认不动用户原来的安排。

备选时段怎么来

按事件时长在当天/次日 8:00–22:00 扫描日历空隙，用规则算而不是让模型提案：零延迟，也不会出现幻觉。

03

不打断用户，但需要提前准备的日程提前一晚提醒

调研依据 · "提醒打扰"顾虑均值 3.96、48.89% 打满分，是顾虑榜里最突出的一项

冲突提示只出现在保存页里，不弹窗、不拦着保存，用户看一眼可以照存。

提前一晚

含"材料 / PPT / 报告 / 准备 / 汇报"等关键词的日程，提醒提前到前一晚 20:00 并改写文案（"请准备 · 明天 14:00 组会"）。"忘记提前准备"是调研里的高频痛点。

平台约束

微信订阅消息是"一次授权一次推送"。预备提醒不再申请额外授权，而是复用该事件唯一的那一次，把它挪到预备窗口发出；验收口径：单事件平均授权请求次数 ≤ 1.5。

Tech · 技术亮点

改了三版提示词，才定下该看哪个数

第一版提示词跑完，端到端完全正确率是 66.2%，15 条 badcase 里 9 条出在"明天""下周""傍晚"这类时间表述上。改一版提示词到底是变好还是变坏，光翻几条语料判断不了：有的从错变对，有的从对变错。于是先造 100 条语料覆盖七类消息形态，按 8:2 固定切分、种子写死，把"解析对不对"拆成五层分别统计，每改一版就重跑全量。到第三版，端到端走到 75.0%，dev 与 test 两侧都过线。

01

单层指标会互相打架，所以只认端到端

v1.1 那版，has_schedule 判定 F1 从 99.2 掉到 97.0，同期事件级查准和端到端却在涨。五层指标都留着看，但决定一版提示词留不留的只有端到端完全正确率。

02

失败点在往多日程集中

三版 badcase 是 15 → 12 → 8 条，结构却在迁移：模糊时间（C 类）从 5 条清零，多日程（D 类）一直卡在 6 条。v1.2 加的"只要表达了未来的行动意图就必须提取"，把"晚上有空的话一起自习吧"这类被当成闲聊丢掉的消息救了回来，C 类一次全清。

03

剩下的错集中在多日程

8 条 badcase 里 6 条是多日程：一条消息里两个事件，排在后面的容易被漏掉。这类问题靠加规则收益递减，规则越多误报风险越大。下一步因此转到了产品侧，把"识别有误"的上报入口做进小程序，用真实 badcase 继续喂评测集。

可复现资产：eval/run_eval.py · eval/corpus/sample.jsonl · eval/gen_corpus.py。线上云函数与评测脚本里各存一份提示词，两边保持逐字一致（各 1804 字符），线上一旦单独改动，跑出来的分数就不再代表线上表现。逐版完整指标、badcase 明细与这套评测的边界，见 解析质量评测报告 →

Position · 竞争定位

不做"提醒生成"，做"日程治理"

微信生态内已有小微（官方 AI 助手）、元宝、滴答清单等"消息 → 提醒"工具，但它们不维护可管理的日程库，也不回答"日程是否冲突、DDL 缓冲是否被透支"，而这恰是调研中的第一需求（70.1%）。本项目把价值落在治理层：解析只是入口。

两个维度看差异：本项目选择"有日程库 × 容量视角"

小微 / 元宝 = 提醒生成（无日程库、只处理单次时刻）；滴答清单 = 任务清单（有库、无冲突治理）；WeSchedule = 日程治理（冲突检测 + DDL 区间 + 容量视角）。若官方能力日后覆盖"消息转日程"，入口层会被稀释，治理层依赖的日程库积累是留下的部分。

Dev Log · AI 协作开发

卡住过的地方，和怎么定位的

功能与 AI 协作完成，"哪里错了、该改哪一层"是自己判断的。

  • 两处静默失败：新建日程写入时少了 reminded 字段，提醒扫描把它当成"已提醒"跳过，日程建好了却永远不进队列；location 为空的日程仍在列表里渲染 null。改法：写入时显式 reminded: false；空值不渲染
  • 提醒锚点算错一天：云函数运行在 UTC，北京时间 00:00–08:00 之间"今天"会被算成前一天，日程锚点落到过去，提醒不会触发。改法：显式 +8 小时后再取日期；靠日志 scanned=12 / sent=0 反查到这一步
  • 剪贴板读取"点了同意也不生效"：两个问题叠在一起：隐私授权 API 名写错，自定义弹窗其实从未注册；回调里回传的 buttonId 在页面上又不存在，微信判定无效，授权态于是存不下来。改法：修正 API 名，弹窗里改成真实的同意按钮并回传它的 id
  • 密钥不进仓库：DeepSeek key 只写在本地 .env，仓库里只有 .env.example，评测脚本从环境变量读。从第一天就这么定，避免提交历史里留下 key

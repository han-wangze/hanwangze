WeSchedule

微信小程序 MVP：把微信群聊消息变成可管理的日程。复制群消息 → 自动解析 → 确认保存 → 订阅消息提醒；不止于"解析成一条提醒"——带软/硬分级的冲突检测、DDL 区间识别与预备提醒，回答"日程装不装得下"。87 人调研、87.4% 接受度，端到端解析准确率 75%。

Why · 痛点与市场

群消息太多，日程总漏

How · 方案架构

一条自动化的解析链路

小程序端捕获剪贴板，云函数调用 DeepSeek 完成结构化解析，落库后通过微信订阅消息实现到点提醒。

技术栈：微信小程序（WXML/WXSS/JS）· 微信云开发（云函数 + 云数据库）· DeepSeek deepseek-chat（temperature=0，JSON 模式）· 微信订阅消息。 个人主体小程序，类目"工具-效率"；系统日历写入经真机验证不可用，故采用"小程序内日程 + 订阅消息提醒"方案。

Smart · 冲突检测与提醒策略

把调研数据翻译成设计决策

调研里三个数字直接约束了这个功能该长什么样：冲突检测是用户第一需求（70.1%），而"提醒打扰"是顾虑榜 5 分占比最高的一项（48.89%），"识别不准"又是顾虑均值第一（4.08）。所以功能不能只"检测出来"，得同时回应这三条约束。

调研数据（约束）由此推导的设计决策
冲突检测需求 70.1%，智能功能中排名第一 保存前自动检测时间重叠并提示，列表页同步标注 ⚠ 角标
"提醒打扰"顾虑均值 3.96，48.89% 打满分（最突出） 非阻断式内联警示：不弹窗、不打断保存流程，用户可忽略并直接保存（成年人的日历本就允许重叠）
"识别不准"顾虑均值 4.08（第一） 凡是 AI 可能出错的环节改用规则：分级只依赖可靠字段 is_deadline，备选时段用规则法扫描而非 LLM

冲突分级：不是所有重叠都同等对待

  • 硬冲突 两个定点事项重叠（会议 vs 会议）→ 强提示 + 给备选时段
  • 软冲突 定点事项 vs DDL → 仅弱提示，不给改期建议

作业截止不是一个"占用时段"，它是一个 deadline——真正的问题是"截止前你有没有空干活"。这个区分让功能明显超出"时间重叠 if 判断"的水平。

关键点：分级只用 is_deadline 这一个已很可靠的字段，不引入新的 AI 输出类型，从而避免了"类型判错 → 冲突等级被错误放大"的连锁风险。

建议时段：AI 提案，人裁决

对硬冲突给出 1–2 个一键采纳的备选时段（chip 按钮："改为周三 16:00？"点一下即改），而不是直接改完让用户确认。

  • 默认不动用户的安排，用户主动采纳才生效
  • 纯规则实现：按事件时长在当天/次日 8:00–22:00 扫描日历空隙
  • 零成本、零延迟、不会幻觉——恰好回应"识别不准"顾虑

区别很微妙但重要：不是"AI 已改，你确认"（默认信任 AI），而是"AI 提案，你选"（默认不动）。

预备提醒 · 以及一个绕不开的平台约束

含"材料 / PPT / 报告 / 准备 / 汇报"等关键词的日程，提醒会提前到前一晚 20:00 发出并改写文案（"请准备 · 明天 14:00 组会"），呼应调研中"忘记提前准备"这一高频痛点。

平台约束：微信小程序的订阅消息是"一次授权一次推送"，提醒次数是受授权次数预算约束的稀缺资源。因此预备提醒复用该事件唯一的一次授权（把推送移到预备窗口），而不是新增一次推送——授权请求越少，用户越可能点"允许"。

验收指标：单事件平均授权请求次数 ≤ 1.5；冲突检测因用规则实现，准确率接近 100%（已知边界：语义级冲突如"午饭撞午饭"不识别）。

实现位置：miniprogram/utils/conflict.js（detectConflicts / findFreeSlots，纯前端零 AI 依赖）· saveEvent 计算 is_prep · remind 云函数按预备窗口调度。

Position · 竞争定位

不做"提醒生成"，做"日程治理"

微信生态内已有小微（官方 AI 助手）、元宝、滴答清单等"消息 → 提醒"工具，但它们不维护可管理的日程库，也不回答"日程是否冲突、DDL 缓冲是否被透支"——后者恰是调研中的第一需求（70.1%）。本项目把价值落在治理层：解析只是入口。

两个维度看差异：本项目选择"有日程库 × 容量视角"

小微 / 元宝 = 提醒生成（无日程库、只处理单次时刻）；滴答清单 = 任务清单（有库、无冲突治理）；WeSchedule = 日程治理（冲突检测 + DDL 区间 + 负载视角）。若官方能力日后覆盖"消息转日程"，入口层会被稀释，治理层依赖的日程库积累是留下的部分。

Dev Log · AI 协作开发

给 AI 系统做工程化度量

本项目以"评测闭环驱动"的方式迭代：先有确定性评测（固定切分 + 相对时间锚点 + 五层指标），再以 badcase 反向改 prompt，每一步都用数字验收。

  • 建评测闭环：100 条语料 + 8:2 固定切分（种子 20260717），五层指标覆盖 has_schedule 判定 / 误报率 / 事件级 P·R / 字段准确率 / 端到端正确率。产出：run_eval.py + corpus/sample.jsonl + gen_corpus.py
  • prompt v1 → v1.2：badcase 驱动，新增时段映射、相对星期未来向、行动意图必提取等规则。结果：端到端 66.2% → 70.0% → 75.0%（dev/test 双达标）
  • 前端体验优化：剪贴板 30 字预览防撑爆布局；确认页日期/时间改用原生 picker。并清理未引用的 event-card 组件与 format.js 死代码
  • 工程化收尾：密钥走本地 .env（不进对话/不进仓库）；一键评测启动器 run_dev.sh/.bat；git 初始化并修复沙箱回滚导致的工作树事故。HEAD = bdc07c4
  • P0 · 云函数时区 bug：云函数运行在 UTC，导致北京时间 00:00–08:00 期间"今天"被算成前一天，日程锚点落在过去 → 提醒永不触发。改为显式 Date.now()+8h + getUTC* 换算。这是"提醒不发"的真正根因，靠日志 scanned=12 / sent=0 反查定位
  • 冲突检测：基于 is_deadline 的软/硬分级 + 非阻断式内联警示 + 规则法空闲槽 chip。刻意不引入新的 AI 输出类型，避免"类型判错 → 冲突等级被放大"。纯前端实现，零云函数改动、零 prompt 改动
  • 预备提醒：识别含准备关键词的日程，复用该事件唯一的一次订阅授权，把推送移到前一晚 20:00 的预备窗口。回应微信"一次授权一次推送"的稀缺性约束，不增加授权请求
